Drill: One Shared Asset Pool

1. Why wasn't "just add more hairstyles" enough?

The user asked for more hair AND for created characters to match NPCs. Why did adding hair to the creator's catalog alone fail the brief?

Answer

NPCs were rigged glTF models that physically can't wear composite parts — hair added to the creator's pool could never appear on a townsperson. The two requests shared a root cause (two unrelated pipelines); only unifying the pool fixes both, after which hair expansion is six data rows both consumers inherit.

2. What was the unification seam?

How much new render machinery did routing all NPCs onto composites require, and why?

Answer

None. The dispatch hook already existed: the loop drew a composite for any NPC with a customLooks entry, else the rigged model. Giving EVERY NPC a look (npcLooks[i]) made the else-branch unreachable for NPCs — the previous feature's hook became this feature's seam.

3. Authored-or-derived

State lookForPersona's decision rule and what each branch buys.

Answer

Valid authored look → use it (art direction: the cop reads uniformed). Otherwise → randomizeLook(FNV-1a(name)): deterministic, so an unauthored NPC keeps the same face every run with no save data, and a stale authored look demotes (with a logged reason) instead of blocking the spawn.

4. Where does look validation happen — and why NOT in the parser?

Answer

PersonaLoader checks structure only (exactly five items — a typo fails loudly like a bad position). Catalog validation lives in lookForPersona at the spawn site, so the persona format has no dependency on the parts catalog and catalog edits can't retroactively break persona files — a removed part just falls back at runtime.

5. The retired models

Unification deleted the rigged NPC look. What was done so this reads as a decision rather than a regression?

Answer

The trade-off was priced and logged: fidelity (skeletal animation, textures) exchanged for one-pool cohesion per the brief's stated priority; loading stays dormant (remote players, revival); and the off-ramp — rebuild both systems on a modular CC0 pack (XL) — is documented in the plan for the day fidelity wins.

6. What does the roster test assert about looks, and why those three properties?

Answer

Every shipped persona has an AUTHORED look (never the hash — keeps the cast art-directed), each validates against the live catalog (no silent fallback drift when parts change), and no two are identical (variety ≥ the old five-model baseline). The interesting promise is checked at the data level, not by eyeballing screenshots.

7. Transfer it

Your app renders emails with template engine A and in-app messages with engine B; product asks for "consistent branding" and "more templates". Map the lesson.

Answer

Same shape: two consumers, two pools. Don't tune B to resemble A — pick one template pool, give both consumers a resolver into it (specific template if authored, derived default otherwise), then "more templates" is data both channels inherit. Assert the brand properties over the shared pool in tests.
