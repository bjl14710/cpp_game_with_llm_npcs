Server-Authoritative Replication

1. A joined client's copy of NPC positions is…

Clients don't simulate at all — the cheapest way to never diverge from the authority is to never compute your own answer.

2. Why does NetServer spawn one reader thread per connection instead of one loop over all sockets?

At 4 players, thread-per-connection is the simplest correct design; poll/epoll multiplexing earns its complexity at hundreds of sockets.

3. The tick thread needs NPC positions for snapshots. How does it get them?

The thread contract: game state crosses into networking only as values through guarded queues. World stays single-threaded; solo play is untouched.

4. Correct shutdown order for a thread blocked in recv():

shutdown() forces the blocked recv to return; join() guarantees the thread is done touching the fd; only then is close() safe (an early close risks the kernel recycling the fd number under the still-running thread). A flag alone never wakes a blocked syscall.

5. Written recall:

Why does the handshake carry kNetProtocolVersion, and what happens on mismatch?

Reference answerDifferent builds may speak different wire formats. The server compares the client's version to its own at JoinRequest time and answers a refusal Welcome with a human-readable reason ("update the game") instead of accepting a peer that would silently desync. One int compared once per join buys away a whole class of bugs.
