Drill 0030 — Diegetic Versus HUD Signalling for Time Pressure

Answer before expanding. Source: lesson 0030, issue #157.

1. Define diegetic vs HUD signalling, and give the trade on precision and attention.
Answer Diegetic exists inside the world the characters inhabit (the sky darkening); HUD is drawn on the glass in front of it (a number). Diegetic is imprecise but free to read — you are already looking at it. HUD is exact but costs a glance away from the game.
2. What single constant made the dusk light a countdown, and what earlier change made that possible?
Answer dayEndHour placed inside DayNight's dusk band (18:00–21:00). It works because #155 inverted the clock's ownership so the match DRIVES the hour — worldHour() sweeps across the investigation phase, making the sky exactly as far through the day as the phase is. The light is not a metaphor for the countdown; it renders the same number.
3. If the sky is already the timer, why draw a HUD at all?
Answer Dusk answers "how much is left" and nothing else. It cannot say which day this is (day 2 of 3 looks like day 1 of 3) or what happens next (it does not distinguish "the vote opens" from "the day ends"). Two short lines cover exactly the questions the diegetic channel cannot.
4. A comment says "if this block ever grows past two lines, the diegetic design has been abandoned". What work is that comment doing?
Answer A HUD grows by accretion, and each addition is individually reasonable. Naming the threshold turns "should we add a progress bar?" from a fresh judgement call into a question with an answer already on record — and states the consequence, which is that the sky coupling becomes dead weight.
5. Why are the HUD's two lines sized 30 and 20 rather than 18 and 16?
Answer raylib's built-in bitmap font computes glyph advance by integer division, so every size from 14 to 18 renders at identical spacing. A "slightly smaller" line at 16 next to 18 is not slightly smaller — it is the same size, and the hierarchy you designed does not exist. Hence the documented 10/20/30/44 ladder.
6. The issue required that settings changed mid-match not affect the running match. Give the weak implementation and the strong one.
Answer Weak: a comment saying not to apply them, relying on every future author reading it. Strong: pendingRules is read at exactly one site — the match.emplace behind "New Mystery" — so no path from the settings page to a live clock exists. Nobody has to remember the rule because no code could break it.
7. Why does Menu exchange two ints with the app layer instead of a MatchRules?
Answer So Menu keeps knowing nothing about MatchClock. The minutes-to-seconds conversion happens in main.cpp. Same separation ModelHooks already keeps by passing model names rather than an LlmClient.
8. The page title was a ternary chain ending in : "Multiplayer". What was the bug, and why did nothing catch it?
Answer Sandbox and Model had been titled "Multiplayer" since the day they were added. The trailing branch served two incompatible roles — "the Multiplayer page" and "any page nobody wrote a case for" — so a missing case was indistinguishable from the last one. No warning, no failure; a screenshot taken for an unrelated reason found it.
9. What is the fix, and name two other places this codebase uses the same technique.
Answer A switch with no default: label, so the compiler names every unhandled enumerator. Also used by phaseName() over MatchPhase and arrestLineFor() over NpcMood.
10. The menu laid rows out as y = h*0.5f - 326.f stepping 72, with ten rows in a 720px window. Do the arithmetic and say what it proves.
Answer Start 34; last row starts at 34 + 9×72 = 682; height 52, so its bottom edge is 734 > 720. Quit had been 14px off-screen the whole time. The arithmetic gives no hint unless you evaluate it with the row count in hand, which nobody does when adding a row.
11. How does deriving the layout from the row count change the failure mode?
Answer step = min(72, (bottom - top) / rows) and height = min(52, step - 6) fit the list to the space available, so adding a row crowds the list but cannot push a button out of the window. The failure becomes impossible rather than invisible. General rule: a layout constant that must agree with a count is a latent bug — derive one from the other.
12. The first attempt at that adaptive layout still had a visible defect. What, and what does it say about deriving bounds?
Answer It started at h * 0.10 and ran "Resume" straight through the word "Paused" — the title is drawn at h * 0.12 in size 40. Deriving the step from the available band is only correct if the band itself excludes everything else already drawn there.
13. Both the title and layout bugs left the test suite green and would have kept it green. What is the actual lesson?
Answer Not "tests are insufficient", but that a class of defect lives exactly where the harness cannot reach — and here that boundary is a hard line: tests/Makefile globs src/core/*.cpp and nothing else, so everything in src/app/ is verified by capture or not at all. Knowing precisely where the line is tells you which changes demand a screenshot.
14. The match hand-back polls match->phase() == Ended rather than reading phase.matchEnded. What does that choice change?
Answer A direct endMatch() call sets the phase without firing a transition. Polling therefore still hands the clock back on the next frame; reading the transition would not. The plaza-gather release IS keyed on the transition, so it stays uncovered — which is exactly what MatchClock::endMatch's doc note warns a future caller about.
15. Why is the hand-back deferred one frame past the Ended transition rather than done on the same frame?
Answer The gather release and any Ended-phase presentation still need to see the clock that produced them. It is safe because Ended is terminal — a new test pins that a day-limit end fires nothing afterwards, so the !fired condition resolves on the very next frame and never again.
