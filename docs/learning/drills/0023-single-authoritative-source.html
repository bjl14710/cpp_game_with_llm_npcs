Drill: The Single Authoritative Source

1. Name the bug class

A character's facing is computed in one system and its movement in another, so it slides backward while animating a forward walk. What is this class of bug called in this codebase, and what is the one-line root cause?

Answer

The moonwalk (first fixed in #61). Root cause: two consumers each reconstruct "the same" quantity from raw inputs instead of deriving it from one shared source, so the copies drift apart.

2. Why not just add pitch to the weapon?

In #91 the weapon aimed yaw-only from the feet while the camera used yaw, pitch, and eye height. Why is "add pitch and eye height to the weapon's own aim code" the wrong fix even though it would look correct immediately?

Answer

It creates a second aim vector that merely agrees today. The next change to look math (or a new weapon) can desync it again. The real fix routes both camera and weapon through one lookDirection(yaw, pitch) so there is no second copy to drift — the bug is designed out, not patched.

3. Space vs time

#91 and #93 are the same principle applied along different axes. State the principle, and say what plays the role of "the one source" in each.

Answer

Principle: a value used in two places should be computed in exactly one place. #91 (space): the shared function lookDirection is the one source both camera and weapon read. #93 (time): the mouse-press event is the one moment the drag-vs-click decision is made; every later frame reads the latch instead of recomputing.

4. Spot the re-sampling bug

float rotateInput = 0.f;
if (IsMouseButtonDown(MOUSE_BUTTON_LEFT) &&
    !menu.pointOverInteractive(GetMousePosition()))
    rotateInput += GetMouseDelta().x * kPreviewDragDegPerPx;

Why does this spin the preview on a control-click, and stall a legitimate drag? What single change fixes both?

Answer

It re-evaluates "over a control?" every frame using the moving cursor. A click that slips off its button mid-press stops reading as a control and spins the figure; a drag that grazes a button momentarily stops rotating. Fix: latch previewDragging once at IsMouseButtonPressed and hold it until the button releases.

5. Derive, don't cache

The idle ease targets player.yawDeg + 180.f recomputed every frame rather than stored once when idling begins. Give one concrete reason the derive-on-read version is safer.

Answer

If the player turns during the idle ease, a cached target would aim the preview at a stale "front" and it would settle facing the wrong way. Deriving from the live player.yawDeg each frame keeps "face the camera" correct as the owner changes — no second copy to invalidate.

6. Why shortestAngleDelta?

The ease uses shortestAngleDelta(previewYaw, defaultYaw) rather than defaultYaw - previewYaw. What goes wrong with the plain subtraction?

Answer

Plain subtraction can be up to ±360°, so the figure can unwind the long way round (e.g. spin 350° left instead of 10° right). shortestAngleDelta wraps the difference to [-180, 180] so the ease always takes the short arc.

7. Generalise it

You review a PR fixing a totals-mismatch bug: the cart shows one total, the invoice another. The diff copies the cart's discount formula into the invoice. What do you comment?

Answer

Same moonwalk shape. Two independently-computed totals that now agree will drift the next time either formula changes. Ask for one shared computeTotal() that both the cart and invoice call, so the number has a single authoritative source.
