Testing Threaded Sockets

1. The loopback suite runs a real NetServer + real NetClients but a fake Ollama. What's the principle?

The threading and framing ARE the code under test — mocking them would verify a program nobody ships.

2. Why does the test server bind port 0?

Hardcoded test ports are a classic source of "passes alone, fails in CI" — some other process owns the port.

3. What's wrong with sleep_for(200ms); CHECK(arrived()); and what replaces it?

eventually(pred, pump, deadline): succeeds the moment the condition holds, fails honestly at the bound. No schedule assumption baked in.

4. FakeOllama deliberately serves responses in 7-byte chunks. Why?

Concurrency/streaming bugs hide in interleavings that "never happen" locally — a good fake makes the ugly case the ONLY case.

5. Written recall:

After changing threaded code, one green test run isn't enough. What did tonight's flake-check protocol look like, and what did it catch?

Reference answerRun the full suite 5-8 times back-to-back after each threading change; investigate any hang with a stack sampler (sample <pid>) instead of killing it. Run 3 of the first batch hung and the two stacks (destructor in join(), worker in cv wait) diagnosed a pre-existing lost-wakeup deadlock in LlmClient's destructor — unrelated to the new code, exposed by more frequent construction of threaded objects.
