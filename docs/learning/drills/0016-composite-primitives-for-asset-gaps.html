Drill: Composite Modeling from Primitives

1. The silent default

You delete the curated "fountain" → "base" mapping and add nothing else. What renders at the fountain's footprint, and why?

Answer

A pseudo-random generic building. modelForBuilding hashes any uncurated id into the generic-buildings pool so filler blocks always get a model. Special cases must be dispatched before that lookup — the fallback can't tell "intentionally uncurated" from "forgot to curate".

2. The invisible water

The first draft put a translucent water cylinder inside the basin, recessed below the rim. Screenshots showed only gray stone. Why?

Answer

DrawCylinder renders a capped solid — the basin's own top cap occludes everything nested inside it. Fix: draw the water as a thin disc floated just above the cap, so it reads as "filled to the brim".

3. Where does the fountain's height live?

The fountain looked squat, so its height was raised from 1.2 to 2.6. Which file/table changed, and why not a constant in drawFountain?

Answer

The SizeSpec table in Assets.cpp — the single sizing source for every rendered entity. A local constant would be a second sizing authority, exactly the stored-state-in-two-places disease the size contracts were built to kill.

4. Radii come from where?

Why does drawFountain derive its radii from the Building's collision AABB rather than taking a radius parameter?

Answer

So the visual footprint and the collider match by construction. If a designer widens the fountain's AABB in City::makeDowntown, the rendered basin widens with it — no second edit, no walk-through gap or invisible wall.

5. Compose or import?

You need (a) a stone obelisk landmark, (b) a pickup truck, (c) a row of planter boxes. Which do you compose from primitives?

Answer

(a) and (c) — convex, low-detail silhouettes a few cylinders/boxes can sell. The truck (b) needs concavity, texture, and reads at close range; composed from primitives it would look like soap bars. Import it.
