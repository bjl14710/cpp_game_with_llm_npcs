Diegetic Versus HUD Signalling for Time Pressure

From issue #157: the match needed a countdown, and the strongest design decision was how little of it to draw.

Diegetic means "inside the fiction"

A diegetic signal exists in the world the characters inhabit: the sky darkening, a shopkeeper closing up, a siren. A HUD signal is drawn on the glass in front of it: a bar, a number, a clock face. Both can communicate "you are running out of time". They cost very different things.

DiegeticHUD
PrecisionLow — "getting late"Exact — "0:21"
Attention costFree; already looking at itMust look away
AmbiguityHigh — is that dusk or a storm?None
Cost to addUsually large; needs world supportTwo lines of DrawText

The reflex is to reach for the HUD, because it is cheap and unambiguous. That reflex is what this issue was written to resist.

The diegetic channel was already paid for

An earlier issue (#155) had inverted the clock's ownership: instead of time ticking while the match watches, the match drives the hour. worldHour() sweeps dayStartHour → dayEndHour across the investigation phase.

Then one constant did the real work:

// dayEndHour sits INSIDE DayNight's dusk band on purpose: that coupling
// is what makes the countdown diegetic, and a test pins it.

DayNight's dusk band runs 18:00–21:00. Setting dayEndHour inside it means the sky is always exactly as far through the day as the phase is. The orange light is not a metaphor for the countdown; it is a rendering of the same number.

The pattern: when two systems already share a variable, a signal in one is a free signal in the other. The expensive part — the sweep, the light model, the fog — existed. Making it a countdown cost one carefully chosen constant and a test that pins it.

So why draw anything at all?

Because the sky answers one question and not the others. Dusk tells you how much is left. It cannot tell you:

  • Which day is this? Day 2 of 3 looks exactly like day 1 of 3.
  • What happens next? Dusk does not distinguish "the vote opens" from "the day ends".

Hence two short lines, and a limit written into the code so the boundary survives the next person to touch it:

// If this block ever grows past two lines, the diegetic design has been
// abandoned and the sky coupling is dead weight.

That comment is doing real work. A HUD grows by accretion — each addition is individually reasonable. Naming the threshold turns "should we add a progress bar?" into a question with an answer already on record.

The constraint that decides your font sizes for you

raylib's built-in bitmap font computes glyph advance by integer division. The practical consequence is blunt:

Sizes 14, 15, 16, 17 and 18 all render at identical spacing. A "slightly smaller" second line at 16 next to a heading at 18 is not slightly smaller. It is the same size, and the hierarchy you designed does not exist.

So the HUD uses 30 and 20 — far enough apart to actually differ. This is not a raylib quirk to route around; it is why this codebase has a documented size ladder (10 / 20 / 30 / 44) and why AsciiText.hpp spends pages on the built-in font's behaviour.

Making "settings cannot affect a running match" structural

The issue required that changing day length mid-match not take effect — changing it mid-day would make the world clock jump. The weak version is a rule in a comment. The strong version is topology:

MatchRules pendingRules;          // the menu writes here
...
match.emplace(pendingRules);      // read at EXACTLY ONE site

There is no path from the settings page to a live MatchClock, because the only read happens where a match is constructed. Nobody has to remember the rule, because there is no code that could break it.

Weak vs. strong invariants. "Do not do X" relies on every future author reading the comment. "There is no way to do X" relies on nothing. When the strong version is available for the same effort, it is always the better trade.

The same reasoning shaped the hook boundary. Menu knows nothing about MatchClock or MatchRules — it reads and writes two ints, and the conversion to real seconds happens in the app layer.

Trailing defaults hide missing cases

A bug this issue tripped over rather than introduced. The page title was selected by a ternary chain:

const char* title = page_ == Page::Main       ? "Paused"
                    : page_ == Page::Controls ? "Controls"
                    : page_ == Page::Creator  ? "Create a Character"
                    : page_ == Page::Journal  ? "Journal"
                                              : "Multiplayer";

Sandbox and Model had been titled "Multiplayer" since the day they were added. Nothing warned. Nothing failed. A screenshot taken for an unrelated reason is what found it.

The trailing branch is serving two incompatible roles: "the Multiplayer page" and "any page nobody wrote a case for". A switch with no default: label separates them — the compiler then names every unhandled enumerator.

switch (page_) {
    case Page::Main:  title = "Paused"; break;
    ...
    case Page::Match: title = "Match Settings"; break;
}   // no default: a new Page is now a warning

The same technique appears twice more in this codebase for the same reason — phaseName() over MatchPhase, and arrestLineFor() over NpcMood.

Magic offsets hide overflow

The menu list was laid out as a fixed start and a fixed step:

float y = h * 0.5f - 326.f;
for (int id : { /* ten ids */ }) { ...; y += 72.f; }

Ten rows: last row starts at 682, is 52 tall, ends at 734. The window is 720 pixels. Quit had been 14 pixels off-screen the whole time. The arithmetic gives no hint — you have to evaluate it with the row count in hand, which nobody does when adding a row.

Deriving the layout from the row count makes the failure impossible instead of invisible:

const float step   = std::min(72.f, (bottom - top) / rows);
const float height = std::min(52.f, step - 6.f);

Adding a row now crowds the list. It cannot push a button out of the window.

Transferable: a layout constant that must agree with a count is a latent bug. Derive one from the other, and the agreement is maintained by construction rather than by whoever edits next.

What the screenshots caught that the tests could not

The suite was green for both title and layout bugs, and would have stayed green. Neither is expressible as a unit test in this codebase — Menu is app layer and is not compiled into the test binary at all. Both were obvious within one second of looking at a capture.

The lesson is not "tests are insufficient". It is that a class of defect lives exactly where your test harness cannot reach, and that boundary is worth knowing precisely. Here it is a hard line: tests/Makefile globs src/core/*.cpp and nothing else, so everything in src/app/ is verified by capture or not at all.
