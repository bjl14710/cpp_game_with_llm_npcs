Inverted-Hull Outlines in an Immediate-Mode Renderer

The Mii-style pass needed every character wrapped in a clean dark line — the single strongest "this is a cartoon" signal. There was no shader pipeline for it, and none was needed: the classic inverted hull does it with the same draw calls the character already uses.

The trick in one paragraph

Draw the object twice. First a slightly enlarged copy in the outline color with front faces culled — so the camera sees only the far, inside-out side of the inflated shell. Then draw the real object normally on top. The real geometry covers the shell everywhere except a thin rim around the silhouette: that rim is the outline, and it follows the silhouette from every angle for free.

Ours, concretely (RaylibRenderer.cpp)

rlDrawRenderBatchActive();                 // flush what came before
rlSetCullFace(RL_CULL_FACE_FRONT);         // show only back faces
for (const PlacedPart& placed : assembled.parts) {
    rlPushMatrix();                        // inflate about the PART's center
    rlTranslatef(at.x, cy, at.z);
    rlScalef(1.06f, 1.06f, 1.06f);
    rlTranslatef(-at.x, -cy, -at.z);
    drawPartRecipe(*placed.part, at, dim, outlineColors);  // all near-black
    rlPopMatrix();
}
rlDrawRenderBatchActive();                 // flush the outline pass
rlSetCullFace(RL_CULL_FACE_BACK);          // restore
// ...then the normal color pass, unchanged.
  • Same recipes, different colors. Because #101 isolated every part shape behind drawPartRecipe, the outline pass is the SAME function with an all-black palette — new parts get outlines for free, including future graphics packs.
  • Inflate about the part's center, not the figure's feet: scaling about the origin would push high parts (hair) outward more than low parts and the rim thickness would vary up the body.
  • Uniform screen-ish thickness comes from the fixed 1.06 factor at roughly uniform character size (everyone is contract-scaled to 1.8u, so 6% is ~5cm of rim everywhere).

Why the batch drains matter

raylib's immediate shapes don't hit the GPU per call — they accumulate in an rlgl batch that flushes later. A GL state change like rlSetCullFace takes effect when the batch is drawn, so without an explicit rlDrawRenderBatchActive() before each switch, the cull mode could apply to geometry queued earlier (or the outline pass could render with the wrong culling entirely). That is also why the two passes are grouped per character instead of interleaved per part: two drains per character instead of two per part.

Where inverted hull is weak

  • Hard-edged meshes (boxes). The technique assumes the enlarged shell stays "outside" the original; at sharp corners the shell's faces move apart and can gap. At our small 1.06 factor and chunky proportions the box rims stayed clean — the escalation path (bigger scale → per-recipe opt-out) was authored in the skill file but never needed.
  • Non-uniform scale in recipes (head_oval's squashed sphere) inherits the hull scale fine because the hull wraps the same matrix stack — but a recipe that drew in world space would escape the inflation. Recipes must stay in the character's local frame.
  • Billboards/sprites don't participate — the mood emote billboard has no hull, which is exactly why it now reads as a style clash (playtest finding #1).
The general shape. When a style effect can be expressed as "draw the same thing again with different state" (outlines, drop shadows, glow shells), reuse the exact draw path with different parameters instead of building a parallel one — one recipe function, two passes, and every current and future asset inherits the effect by construction.
State changes in batched renderers. Any time you touch GL state around immediate-mode draws (cull face, blend mode, depth), flush the batch first — invisible reordering bugs otherwise land on whatever happened to share the batch.
