1. What Silmulator Is (and What Problem It Solves)

Embedded firmware talks to lab instruments — oscilloscopes, power supplies, function generators — using a language called SCPI (Standard Commands for Programmable Instruments, pronounced "skippy"). A real SCPI session looks like this:

// C firmware — send command over VISA/GPIB/USB-TMC
visa_write(handle, "VOLT 5.0");    // set PSU to 5 V
visa_write(handle, "OUTP ON");     // enable output
char* resp = visa_query(handle, "MEAS:VOLT:DC?");  // read back

The problem: you can't run that code without the hardware present. Silmulator replaces the physical rack with virtual blocks that respond to the same SCPI commands the real instruments would, so you can develop and debug your firmware at a laptop, on a plane, or in CI.

💡 Key insight
The simulated instruments in Silmulator are spec-faithful. VOLT 5.0 sent to the virtual Power Supply actually changes its internal state, and MEAS:VOLT:DC? returns a numeric string just like the real Keysight E36312A would.

2. The Three-Step Workflow

Every Silmulator session follows the same loop:

  1. Place — drag hardware blocks onto the canvas
  2. Connect — draw wires between ports
  3. Drive — send SCPI commands (manually via console, or by loading your source code)

Step 1 — Place blocks

Open the Library panel on the left. Double-click any instrument name, or hit the Add Selected Block button. You can also use the toolbar buttons across the top or the Add menu. The block appears on the canvas; subsequent blocks auto-place so they never stack.

Step 2 — Connect ports

Each block has connection ports — the small blue circles on its edges. To wire two ports:

  1. Click and hold on the source port. A dashed gold line appears.
  2. Drag to the destination port on another block.
  3. Release. The wire turns solid gold when connected.

The connection is bidirectional in the sense that SCPI commands flow along it based on which block is "driving" the conversation.

⚠ Ports
You can only connect a port to one other port at a time. A green port dot means connected; blue means free; a gold hover highlight shows where a wire would land.

Step 3 — Drive with SCPI

Two ways to send commands:

  • SCPI Console (bottom panel) — select a block on the canvas, type a command, hit Send or Ctrl+Enter. Response appears immediately.
  • Code Input block — paste C, C++, or Python source code. Silmulator extracts every visa_write / visa_query call and can replay them to the connected hardware blocks in order.
-- SCPI Console example session --

> Select the Power Supply block, then type:
VOLT 3.3          → (no response — write command)
VOLT?             →  3.3000000E+00
OUTP ON           → (no response)
MEAS:VOLT:DC?     →  3.3000000E+00

How a SCPI command travels through the code

When you type VOLT 3.3 in the console and press Send, here is the exact path:

1. ConsolePanel._send()                      main_window.py:123
   → selected block.send_command("VOLT 3.3")

2. BaseBlock.send_command()                  base_block.py:203
   → self.device.process("VOLT 3.3")

3. BaseDevice.process()                      base_device.py
   → ScpiParser.parse("VOLT 3.3")
   → looks up handler in self._handlers["VOLT"]

4. PowerSupply._set_voltage()                power_supply.py
   → channel.voltage = 3.3

5. Response string returns back up the chain
   → ConsolePanel logs it
💡 The big picture
The wire on the canvas represents a potential connection but doesn't route SCPI in the Python layer — the command goes directly from the Console to whichever block is currently selected. Wires matter when the Code Input block runs parsed commands: it fans them out to whatever blocks its output ports are connected to.

4. Often Confused: SIL vs HIL vs CIL

Silmulator's full name is "SIL/HIL/CIL Hardware Simulator." These three terms are often used interchangeably but mean different things:

AcronymFull nameWhat runs on real hardwareWhat is simulatedTypical use case
SIL Software-in-the-Loop Nothing — everything is software Both the ECU/MCU and the instruments Pure algorithm correctness; no hardware at all
HIL Hardware-in-the-Loop The real embedded controller (MCU/ECU) The instruments / plant it connects to Real-time controller testing; firmware timing matters
CIL Code-in-the-Loop Nothing; the source code is the input Both the MCU and the instruments Checking measurement code logic before flashing

How Silmulator fits:

  • When you paste a C file into the Code Input block and run its SCPI calls against simulated instruments — that is CIL.
  • When you run compiled firmware on a real MSP430 and use Silmulator's simulated oscilloscope/PSU over a real VISA connection — that would be HIL (Silmulator is the "plant").
  • When both the code and hardware are simulated as Python objects — that is SIL.
📌 The key distinction
SIL = algorithm correctness, no timing guarantees
HIL = real hardware runs in real time
CIL = source code is the unit under test; instruments are simulated

6. Check Your Understanding — Scenarios

Scenario A: A teammate says "Silmulator crashed when I clicked File → New after wiring up a big layout." Why did this happen before the recent fix, and how is it fixed now?
Show answer
MainWindow._new_canvas() called QGraphicsScene.clear(), which deleted the C++ Qt items. But CanvasScene._blocks and _wires dictionaries still held Python references to those deleted objects. The next call to to_dict() or reset_all() touched the deleted items → RuntimeError.

The fix: CanvasScene.clear() is now overridden. It calls super().clear() and then resets _blocks = {}, _wires = {}, _connecting = None, _temp_wire = None. Everything in from_dict() that manually reset those dicts was also removed to avoid duplication.
Scenario B: You build a layout with a Function Generator, save it as my_bench.sil, and reopen it. The Function Generator is gone and its wires disappeared. What was the bug?
Show answer
FunctionGeneratorBlock.__init__ passed device_type = "Function Gen", but the registry key in BLOCK_REGISTRY is "Function Generator". When to_dict() saved the block it stored the string "Function Gen". When from_dict() loaded it, BLOCK_REGISTRY.get("Function Gen") returned None — so the block was silently skipped, and all wires referencing its port IDs were dropped.

Fix: the device_type argument is now "Function Generator" to match the registry exactly.
Scenario C: You want to test a large firmware project (a full RTOS tree with dozens of .c files). Walk through the steps in Silmulator.
Show answer
1. Add the hardware blocks the firmware talks to (e.g. Power Supply + Oscilloscope).
2. Add a Code Input block and connect its OUT1/OUT2/OUT3 ports to the hardware blocks.
3. Right-click the Code Input block → Load project folder… and point it at the RTOS root. Silmulator walks the tree, parses every .c/.cpp/.py file, extracts all visa_write / visa_query calls, and shows how many SCPI calls were found.
4. Right-click → Run parsed commands to replay the calls in file/line order to the connected hardware blocks.
5. Open each hardware block's View command log to see what it received and responded.
