One Implementation Across a Language Boundary

From issue #304: a Python probe needs a C++ prompt, and the obvious shortcut would have made the measurement meaningless.

The setup

The game assembles an NPC's system prompt in C++, from five sections in a tested order. A Python harness needs that same prompt so it can ask a model a question and measure the answer. The boundary has to be crossed somehow.

Two options, and they are not close.

A. Re-implement the assembly in Python.
B. Add a mode to an existing C++ tool that prints it, and shell out.

Why A is not merely "duplicated code"

Duplication is normally a maintenance cost: two things to change, and one day you change only one. That framing understates the problem here, and the reason is specific to what the harness is for.

Role.hpp spends thirty lines explaining that the role block's placement is the design — after trait reinforcement, before the action protocol — and that earlier placement was measured to corrupt the action protocol, with the killer emitting call_police on three of five turns.

The probe exists to measure the consequences of placement. A Python copy would have its own placement. So the measurement would be of the copy, not of the game — and it would look exactly like a real result.

That is the difference between a bug and an invalid instrument. A bug gives a wrong answer you can eventually notice. An invalid instrument gives a plausible answer, indefinitely.

The precedent that was already in the codebase

This argument had been made once before, on the other side of the same exchange. tools/eval_lines.py's first gate parses model replies — and does it by shelling out to persona_prompt --parse:

// --parse exists for the same reason on the other side of the exchange:
// tools/eval_lines.py must judge a candidate reply with the REAL
// parseDirectives, not a Python reimplementation of it.
// tools/bench_npc_models.py duplicates the mood keyword list in Python and
// its own comment admits it has to be hand-synced; this avoids repeating that.

Note the third sentence. A sibling tool did take the shortcut, and its own comment concedes the list must be hand-synced. The codebase contains both the pattern and the counterexample, with the counterexample admitting fault.

Reading habit worth having: when you face a design question, check whether the codebase already answered it — and whether it also contains the version that answered it wrong. The failed variant is usually more instructive than the successful one.

What the seam looks like

The new mode takes the state as JSON and renders it through the identical overload the game calls:

std::cout << persona.renderSystemPrompt(state.value("memory", ""),
                                        state.value("gossip", ""), resolved,
                                        roleBlock);

One line, and the entire value of the mode is that it is the same line Npc::ask runs. Everything else in the function is argument preparation.

Inverting a policy at the measurement boundary

The game, meeting an unknown trait id, demotes it with a log and carries on. That is right: a player must not lose an NPC because someone typed gossipy as gosipy.

The tool refuses. Same input, opposite policy, and both are correct — because they answer to different duties:

GameMeasurement
Worst outcomeA player loses a characterA number that means nothing
So on bad inputDegrade and continueRefuse and say why

A measurement taken with a silently missing trait is worse than no measurement, because it still produces a number and that number enters a comparison. Hence also: every failure path prints zero bytes of prompt. A partial prompt would read as a result rather than as a broken fixture.

The check that keeps the seam honest

One assertion carries most of the weight:

An uncast persona must render BYTE-IDENTICALLY through --state
and through the plain mode.

It is the role layer's own contract ("a persona with no role must render byte-identically to today") restated at the tool boundary. Its value is what it protects: probes work by comparing a prompt with a role block against one without. If the two paths differ by so much as a newline, that comparison measures the tool instead of the role — and again, it still yields a number.

Where the tests could not go

tests/Makefile globs src/core/*.cpp and nothing else, so tools/ is outside the test binary entirely — the same boundary that leaves src/app/ uncovered. The contract checks are a shell script.

The reasoning is worth copying: rather than treating "untestable in the harness" as untestable, identify what the harness does cover (the core contract is pinned at test_role.cpp:294) and write a check for the residue — here, whether the tool passes the right arguments to already-tested code.

The general shape

  • When a second language needs a behaviour, export the behaviour, do not re-derive it — a subprocess and a JSON file are cheap.
  • Weigh duplication by what the copy is used for. A duplicated constant is a maintenance cost; a duplicated implementation of the thing you are measuring invalidates the measurement.
  • At a measurement boundary, fail closed even where the product fails open.
  • Pin the seam with an identity check against the path that already worked.
