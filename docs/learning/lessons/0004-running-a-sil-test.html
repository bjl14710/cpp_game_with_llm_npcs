01 The End-to-End Picture

Lesson 0001 showed you the three-step workflow in the abstract: Place → Connect → Drive. This lesson makes it concrete by walking through a real SIL test from start to finish — raw C firmware code in, SCPI responses out.

Here is what happens inside Silmulator from the moment you paste firmware code to the moment the simulated instrument answers:

CodeParsercode_parser/base_parser.py

Each stage is a real class in the codebase. Understanding this pipeline is the key to knowing what Silmulator can and can't do.

02 Step 1 — Place and Connect the Blocks

For a typical SIL test you need at least two blocks on the canvas:

  • Code Input — the block that holds your firmware source and routes extracted SCPI calls.
  • One or more instrument blocks — the simulated hardware your firmware talks to (Oscilloscope, Power Supply, etc.).
  1. From the Library panel (or Add menu), add a Code Input block and an Oscilloscope block.
  2. Draw a wire from Code Input → OUT1 to Oscilloscope → CH1_IN. The Code Input block has three output ports (OUT1, OUT2, OUT3) on its right edge, one per connected instrument.
  3. If your code talks to multiple instruments (e.g. a power supply and an oscilloscope), add each instrument, wire a separate OUT port to each one.
ℹ️
The Code Input block's three OUT ports are defined in silmulator/gui/blocks/code_input_block.py:51-53: 
add_port("OUT1", "OUT1", 1.0, 0.3)   # right edge, 30% down
add_port("OUT2", "OUT2", 1.0, 0.5)   # right edge, 50% down
add_port("OUT3", "OUT3", 1.0, 0.7)   # right edge, 70% down
x_frac=1.0 puts them on the right edge; y_frac positions them vertically.

03 Step 2 — Paste and Parse Your Firmware Code

Double-click the Code Input block to open the code editor. Paste your C, C++, or Python code on the left; the right pane shows extracted SCPI commands in real time when you click Parse.

What the parser recognises

The parser (silmulator/code_parser/base_parser.py) scans each line against a list of known C/C++ and Python patterns. These are the C patterns it looks for:

# C/C++ write patterns (from C_WRITE_PATTERNS in base_parser.py)
viWrite(session, "VOLT 5.0")         ✓ extracted
visa_write(dev, "OUTP ON")            ✓ extracted
scpi_send(handle, "ACQ:STATE 1")       ✓ extracted
ibwrt(dev, "TRIG:A:LEVEL 1.5")       ✓ extracted

# C/C++ query patterns
result = viQueryF(session, "MEAS:VOLT:DC?")  ✓ extracted as query

# Python patterns
inst.write("VOLT 5.0")                ✓ extracted
result = inst.query("MEAS:VOLT:DC?")   ✓ extracted as query

After extraction each command becomes a ParsedCommand object:

silmulator/code_parser/base_parser.py
@dataclass
class ParsedCommand:
    scpi_command: str        # e.g. "VOLT 5.0" or "MEAS:VOLT:DC?"
    line_number:  int        # where it appeared in the source
    source_language: str    # "c" or "python"
    context:  str = ""      # first 80 chars of the original line
    is_query: bool = False  # True if ends with ?
    variable_name: Optional[str] = None  # e.g. "result" for query assignments

The block face shows a live tally: "SCPI calls found: 6" and a preview of the last four commands.

⚠️
The SCPI heuristic is not infallible. The parser uses a regex that matches strings starting with *WORD or WORD[:] — it can miss commands buried in preprocessor macros, variadic format strings, or indirect string construction. Real embedded code that builds SCPI strings dynamically (e.g. sprintf(buf, "VOLT %f", v)) will be extracted as VOLT <VAR> — the variable part is replaced with the literal <VAR> placeholder.

04 Step 3 — Run and Read the Responses

Right-click the Code Input block → Run parsed commands. This calls _run_commands():

silmulator/gui/blocks/code_input_block.py:163
def _run_commands(self) -> None:
    """Route parsed SCPI commands to connected blocks."""
    if not self._parsed_commands:
        return
    connected_blocks = self._get_connected_blocks()
    for parsed_cmd in self._parsed_commands:
        for block in connected_blocks:
            block.send_command(parsed_cmd.scpi_command)

Key things to notice:

  • _get_connected_blocks() walks all three OUT ports and collects every instrument on the other end of a wire. If you have two instruments wired up, every parsed command is sent to both — there is no routing-by-instrument-type. Connect only the instruments your firmware actually talks to.
  • block.send_command() calls the instrument's device.process(cmd) which returns the SCPI response. Responses appear in the block's SCPI Console panel (bottom of the window) or in the block's right-click context menu output.

What does the instrument actually do with the command string? It goes through the ScpiParser:

silmulator/scpi/parser.py
@dataclass
class ScpiCommand:
    path:     str         # e.g. "MEAS:VOLT:DC" (normalised, no ?)
    is_query: bool        # True if ends with ?
    params:   List[str]   # e.g. ["5.0"] for "VOLT 5.0"

The parser splits compound commands on ;, strips the ? suffix, uppercases the header path, and separates parameters. The device handler then looks up the path in its command table and either sets a value or returns one.

05 Snippet Mode vs Project Mode

The Code Input block has two input modes. Both end up in the same parse → run pipeline; the difference is how you get code in.

ModeHow to activateWhat it parsesBest for
Snippet Double-click the block A single text buffer you paste manually Quick experiments, one-off command sequences
Project Right-click → "Load project folder…" Every .c, .cpp, .py file in the chosen directory tree, in file/line order Full firmware trees (RTOS, flight SW), full-system SIL runs

In project mode the block face shows:

Project: my_firmware/
Files: 12/47  ← parsed / total recognised
SCPI calls found: 38

The "Right-click → Refresh project" action re-parses all files without closing the block — useful when you edit the firmware and want to re-run immediately.

💡
Often confused: "Run parsed commands" vs "Send SCPI command" (in the SCPI Console). Run parsed commands fires the entire list extracted from source code, in order, broadcasting to all connected instruments. Send SCPI command sends a single command you type manually to the selected block. Use the Console for interactive debugging; use Run for automated replay of your firmware's command sequence.

Check Your Understanding

Q1. You paste firmware C code into snippet mode and click Parse. The right panel shows zero commands. Your code contains scpi_send(handle, "ACQ:STATE 1");. What is the most likely cause?

  • scpi_send is not a recognised C pattern — only viWrite and ibwrt are supported.
  • The language dropdown is set to 'auto' and auto-detection picked 'python' instead of 'c', skipping all C_WRITE_PATTERNS.
  • The Code Input block is not connected to any instrument block yet, so Parse returns nothing.
  • The _deduplicate() method removed the command because it appears twice in the code.

Q2. _run_commands() loops over connected_blocks for every parsed command. Your Code Input has OUT1 wired to a Power Supply and OUT2 wired to an Oscilloscope. What happens when the firmware contains both VOLT 5.0 and ACQ:STATE 1?

  • VOLT 5.0 goes only to the Power Supply; ACQ:STATE 1 goes only to the Oscilloscope — Silmulator routes by command prefix.
  • Both VOLT 5.0 and ACQ:STATE 1 are sent to both the Power Supply and the Oscilloscope; each instrument silently ignores commands it doesn't recognise.
  • Only the first parsed command is sent; run must be clicked once per command to advance through the list.
  • The run raises an error because VOLT is not a valid oscilloscope command.

Q3. Your C firmware uses sprintf(buf, "VOLT %f", voltage); visa_write(dev, buf); to build a command dynamically. What does the Code Input block extract?

  • It extracts the correct command with the runtime value of voltage substituted in.
  • It extracts the sprintf format string literally — something like VOLT %f — because the parser reads string literals, not runtime variable values.
  • It extracts nothing — the parser skips sprintf() because it's a formatting call, not a VISA call.
  • It extracts the command once for each unique value of voltage it can infer from the source code.

Q4. In project mode you load a firmware folder. The block face shows "Files: 12/47". What does the 47 represent?

  • The total number of instrument blocks Silmulator supports connecting at once.
  • The total number of SCPI commands found across all files (12 matched, 47 total).
  • The total number of source files found in the folder tree; 12 of them were successfully parsed.
  • The number of files still pending — 12 are loaded; 47 remain to be loaded on the next refresh.

Q5. You run parsed commands against the Power Supply. The SCPI Console shows a response of 5.00001 for MEAS:VOLT:DC? even though you set VOLT 5.0. Is this a bug?

  • Yes — the power supply block is miscalibrated and needs reset with *RST before measurements are reliable.
  • No — Silmulator intentionally adds small Gaussian noise (~1e-5 relative) to measurements to mimic real instrument behavior.
  • Yes — you need to issue *RST after setting VOLT to flush the noise accumulator.
  • Yes — the C++ SCPI parser is not built, so the Python fallback introduces extra floating-point rounding.
