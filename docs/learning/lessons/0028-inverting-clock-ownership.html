Inverting a Clock's Ownership Without Disturbing Its Consumers

From issue #155: the detective match takes over the world clock, dusk starts landing exactly when the vote opens — and not one of the six systems that read the hour was touched.

The shape of the problem

Before this change the game had one clock and one way to move it:

world.state().advanceTime(dt);   // fmod over 24 hours, fixed 60x scale

Six systems read the result: NPC schedules, the day/night sky, the fog light level, NPC behaviour, the gossip tick, and the journal's timestamps. None of them holds its own timer. They all read one shared value.

A match needs the opposite relationship. Instead of the clock ticking while the match watches, the match owns pacing and drives the hour: the investigation phase sweeps 09:00 → 20:00 across its duration, so the sky is always exactly as far through the day as the phase is. Dusk becomes a countdown timer that needs no UI at all.

The inversion in one line. Free roam: time passes, the match would observe it. A match: the phase advances, and time is computed from it. Same variable, opposite direction of causation.

Why this cost nothing to the six consumers

Because they were coupled to a value, not to a call. Every consumer does some version of:

const float worldHour = static_cast<float>(world.state().timeOfDayHours());

Nobody calls advanceTime. Nobody subscribes to a tick event. Nobody caches an hour across frames. So swapping the thing that writes timeOfDayHours is invisible downstream — the read side cannot tell the difference and does not need to.

Contrast the version of this codebase that would have made the change expensive:

If the consumers had been…What #155 would have cost
Subscribed to an onHourChanged event Two publishers to reconcile, and ordering bugs when both fire
Each holding float myHour_ advanced by their own dt Six independent drifts; the match could only ask nicely
Calling advanceTime() themselves Six call sites to find, and the clock advancing six times per frame
Reading one shared value (what we have) One write site changes. Nothing else moves.

Enforcing "exactly one owner"

The issue was explicit: "The match drives it or advanceTime does, never both — assert this rather than assuming it."

The tempting implementation is a flag and two branches scattered where each is convenient. That is exactly how you end up with both running: someone adds a third call site during a later feature and nothing complains. The implementation instead collapses both owners into a single function, so there is no second place to get it wrong:

PhaseTransition advanceWorldClock(WorldState& state,
                                  std::optional<MatchClock>& match, float dt) {
    if (!match) {
        state.advanceTime(dt);          // free roam: time passes
        return PhaseTransition{};
    }
    const PhaseTransition fired = match->advance(dt);
    state.setTimeOfDayHours(match->worldHour());   // a match: time is derived
    return fired;
}
The optional is the assertion. There is no bool matchRunning that could disagree with reality. Whether the std::optional<MatchClock> holds a value is the answer to "who owns the clock", so the two facts cannot drift apart. A state machine with one representation cannot be in an inconsistent state.

Proving the untouched path really is untouched

"Free roam is unaffected" is the kind of claim that is easy to assert and easy to be wrong about. The check that actually settles it:

./build/cpp_game_with_llm_npcs --frames 240 shot.png --camera 0 30 180
# before the change and after the change
md5 -q shot_baseline.png shot_after.png
5d4937aa85c299c292597e6dbc276dae
5d4937aa85c299c292597e6dbc276dae

A fixed frame count, a fixed camera, and a deterministic world produce a byte-identical PNG. Not "looks the same" — the same bytes. That is worth building the harness for once, because it converts a judgement call into a comparison.

The Intro phase, and naming things you could have overloaded

A match now opens on MatchPhase::Intro before the first Investigation. The cheap alternative was to reuse Resolution on "day zero" — same duration, same hold-the-clock behaviour, no new enum value.

Resist that. A phase that means something different should not borrow another's name. Every switch on MatchPhase downstream — the vote, the gather, the phase HUD — would have to ask "is this a real Resolution or the fake day-zero one?", and each of them would have to get that right independently. One enum value is far cheaper than a condition repeated at every site.

Note also what Intro does to worldHour(), which is not what the other non-Investigation phases do:

if (phase_ == MatchPhase::Intro) return start;      // 09:00 — the day has not begun
if (phase_ != MatchPhase::Investigation) return end; // 20:00 — Vote, Resolution, Ended

Vote and Resolution hold at dusk because the day is spent. Intro holds at dawn because it has not started. Sharing the "hold the clock" behaviour while differing on which value to hold is precisely the distinction the separate enum value buys you.

The diegetic coupling, and the test that guards it

MatchRules::dayEndHour is 20.0. DayNight's dusk band runs 18.0 → 21.0. That overlap is not a coincidence, it is the feature: the vote opens while the sky is visibly going orange, so the player feels the deadline without a single HUD element.

A coupling that load-bearing and that invisible needs a test whose failure message explains itself:

TEST_CASE("the vote opens inside the dusk band, so the light is the countdown") {
    const MatchRules rules;
    CHECK(rules.dayEndHour > daynight::kDuskStart);
    CHECK(rules.dayEndHour < daynight::kDuskEnd);
}

Without it, a later retune of either constant silently costs the game its only piece of UI-free signalling, and nothing fails.

What to take away

  • Coupling consumers to a shared value rather than to a producer call is what makes a producer swappable later.
  • To enforce "exactly one X", give the system one representation of which X is active, not a flag plus a convention.
  • Collapse mutually exclusive branches into a single call site; a rule you cannot express in the type system, express in the topology.
  • A new enum value is cheaper than a condition repeated at every switch downstream.
  • When you claim a path is unaffected, produce the byte-identical artefact rather than the argument.
