Layering a Temporary Override Over Authored Content

From issue #156: the whole town has to assemble in the plaza for the vote, then go back to their lives — without a single line of personas/*.persona changing.

The problem, and the two bad answers

Every resident has an authored day. It lives in their persona file as a list of ScheduleEntry blocks — be at this position, doing this activity, between these hours:

struct ScheduleEntry {
    float startHour = 0.f;
    float endHour   = 0.f;
    Vec3  position{};
    std::string activity;
};

Now a new phase needs everyone somewhere else, temporarily. Two answers present themselves immediately, and both are wrong.

Bad answer 1: rewrite the schedule. Push a "be at the plaza" entry onto everyone's list when the vote opens, pop it afterwards. This fails on restore. You now have to remember exactly what you changed, per NPC, and undo it precisely — and any code path that skips the undo (a crash, an early exit, a transition nobody anticipated) corrupts authored content permanently. You have turned read-only data into mutable state.

Bad answer 2: a mode flag. Add bool gathering_ and branch the whole movement block on it. This duplicates the walk: one copy for schedules, one for gathering. The two copies then drift, and the second one is always the worse one, because the first had years of edge cases beaten into it.

The shape that works: a nullable destination consulted first

The override is not a mode and not an edit. It is one nullable field that outranks the authored answer at the exact point the authored answer is looked up:

const Vec3* target = nullptr;
if (gatherTarget_) {                       // the override wins...
    target = &*gatherTarget_;
} else if (active >= 0) {                  // ...otherwise the authored day
    target = &schedule_[active].position;
}
if (target == nullptr || dist < kSchedulePause) break;
// one walk, shared by both
The property that makes this cheap: restoring costs nothing. gatherTarget_.reset() is the entire undo, and it needs no memory of what was there before, because nothing was ever overwritten. The authored schedule was out-ranked, not suspended.

Notice what did not change: there is still exactly one walk. A resident summoned to the plaza is moved by precisely the code that already moves them to the bakery — same steering, same collision resolution, same pause when the player is close enough to talk.

Out-ranked, not suspended — and you can see the difference

The distinction is not pedantry; it is visible in the game. The activity label still reports the authored day while the override is walking someone somewhere else:

if (hasSchedule) {
    activity_ = active >= 0 ? schedule_[active].activity : std::string();
}

Marge is still "baking bread" on her nameplate while she walks to the vote, because as far as her authored day is concerned, she is. That reads correctly to a player: she has been pulled away from something.

The guard that made this a one-field change

The pre-existing early return looked like this:

if (timeOfDayHours < 0.f || schedule_.empty() || state_ != NpcState::Idle) break;

Three conditions bundled together, and they are not the same kind of thing. state_ != Idle means something else owns this NPC's movement — combat, death, an arrest. That one must still stop an override cold. The other two only mean there is no authored answer right now, which an override does not care about. Splitting them is what lets a resident with no schedule at all still gather:

if (state_ != NpcState::Idle) break;                 // still absolute
const bool hasSchedule = timeOfDayHours >= 0.f && !schedule_.empty();
Splitting a guard is a behaviour change until you prove it isn't. The activity_ assignment had to be re-wrapped in if (hasSchedule), because the old code returned before touching the label and therefore kept its previous value. Clearing it in the new structure would have been an unrelated behaviour change smuggled in under a movement fix — the kind that surfaces three months later as "why do nameplates go blank in the sandbox?"

Where the override is set and released

The orchestration lives one layer up, over the whole roster:

void World::setPlazaGather(bool gathering) {
    if (!gathering) {
        for (Npc& npc : npcs_) npc.clearGatherTarget();   // EVERYONE, dead included
        return;
    }
    ...
}

Release is unconditional on purpose. A resident who died holding a destination is still holding it; "released except the corpses" is exactly how somebody turns up standing in the plaza the next morning.

Keying the release on entry, not exit

The subtler decision. The obvious trigger is "when we leave the Vote phase" — and it is wrong, because the reveal happens in the phase after the vote. Releasing on exit empties the plaza at the moment the scene pays off.

Keyed on…Consequence
from == VotePlaza empties during the reveal. Wrong.
dayAdvancedCorrect for the ordinary rollover, misses a match that ends out of the vote.
to == Investigation \|\| matchEndedEvery path back to normal life releases, including ones not yet written.

Keying on the state being entered rather than the one being left makes the release total. Clearing when nobody is gathered is a harmless no-op, and that is the point: the release cannot be missed by a transition nobody thought of.

The map fact that no amount of code review would have found

The gather point "is the plaza centre" — obvious, and unusable. City.cpp authors Gus's hot dog cart as a solid collider spanning x ∈ [-3, 3], z ∈ [-2, 2]. zoneCentre("plaza") returns (0, 0). The computed centre is inside a building, so the obvious implementation walks twenty-one residents into a wall and leaves them shoving at its edge.

The codebase had been telling us for months, in a log line nobody chased:

[llm_npc] mystery: no clear spot in zone "plaza" — body placed at the
          zone centre, which may be inside a building
Transferable habit: when a spatial default "obviously" works, go read what is actually authored at that coordinate. A geometric centre is a statement about bounds, not about emptiness.

The fix is a ring of radius 8, derived from the zone so it cannot drift from the map — and deliberately not formation logic. No ordering rule, no facing rule, no re-packing when someone dies. A gap in the circle is the "who is missing?" signal the scene exists for.

The test trap this change walked into

The first version of the test fixture placed residents at (-70, -52) — a sensible-looking spot near the bakery. It is inside the bakery's collider. Nobody moved, and every movement assertion passed or failed for reasons that had nothing to do with the feature under test. Worse, the regression test ("an NPC with no override moves exactly as before") passed, because both the before and after cases were pinned in place by a wall.

A movement test that never moves is a test that always passes. When asserting that something travels, assert the travel first — a fixture that cannot move makes every downstream claim vacuous.

Recognising this pattern elsewhere

The same shape solves any "temporarily override authored data" problem: a difficulty modifier over authored enemy stats, a debug camera over the gameplay camera, an admin locale over a user's preference. The three properties to look for:

  • The override is nullable, so absence is representable and is the default.
  • It is consulted at the single point the authored value is read — not branched around the consumer.
  • Restore is reset, not replay: nothing was overwritten, so nothing has to be remembered.

If restoring requires knowing what was there before, you built bad answer 1.
