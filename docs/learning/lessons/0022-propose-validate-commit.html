Lesson 0022 · LLM engineering · from PR #89 (gossip)

Propose, Validate, Commit: LLMs Never Write Directly

Gossip needs the model to CREATE game state — the facts NPCs learn. Letting model output write into the world directly turns every hallucination into corrupted state. The discipline:

PROPOSE   the model returns a strict-JSON array of ≤2 candidate facts
VALIDATE  code parses (non-throwing), normalizes subjects, checks types,
          directions, lengths — anything wrong yields NOTHING
COMMIT    only validated records touch the WorldState bus; ids hash
          subject+content so repeats are idempotent

Design choices that make it robust

  • All-or-nothing validation: one malformed entry rejects the whole proposal — no partial commits from half-good output.
  • Idempotent ids: factIdFor(subject, content) is a stable hash, so the same statement extracted twice is one fact, and the first teller's timestamp/source survive re-commits.
  • Normalization at the boundary: subjects squeeze to [a-z0-9_] on the way in, because the journal compares them exactly. Comparable fields beat free paragraphs.
  • Failure is silence: prose instead of JSON logs one line and commits nothing. Facts are a bonus; a crash would be a bug.

Propagation is state, not messages

Spread is a tick over the shared store: pairs within 6 units, teller knowledge older than 30 game minutes, 35% roll, at most one fact per pair per tick. No NPC→NPC message channel exists — so the journal (and any future reader) plugs into the same store with zero new wiring, and the conservative gates keep a secret's spread traceable and slow enough to walk back.

Contrast with the directive tags. [[ACTION:]] tags are also validated (parseDirectives), but they are TRANSIENT — a bad tag wastes one turn. Facts are PERSISTENT state; the validation bar is higher because mistakes compound.
