Length-Prefixed Framing over TCP

Why FrameAssembler exists, and why "just send the JSON" doesn't work.

The problem: TCP is a byte stream, not a message service

TCP guarantees bytes arrive in order and uncorrupted — but it says nothing about where one write ends and the next begins. If the host sends {"type":"Welcome"} and then {"type":"WorldSnapshot",...}, the client's recv() might return both glued together, or the first half of one, or three bytes of a length header. Anything.

Every "works on my machine, breaks over Wi-Fi" protocol bug starts with code that assumes one send() equals one recv(). It never reliably does.

Two classic fixes

StrategyHowWhere this repo uses it
Delimiter framingEnd every message with a byte that can't appear inside it (e.g. \n)StreamAssembler — Ollama's NDJSON stream, one JSON object per line
Length-prefixed framingSend the payload size first, then exactly that many bytesFrameAssembler (src/core/NetFraming.hpp) — all multiplayer traffic

Delimiters are great when the sender guarantees the delimiter never appears in a message (NDJSON promises exactly that). For our own protocol we chose a 4-byte big-endian length prefix: no escaping rules, O(1) "do I have a full message yet?" checks, and binary-safe if we ever move off JSON.

The wire format

[ 4 bytes: payload length, big-endian ][ length bytes: JSON payload ]
[ 00 00 00 11 ][ {"type":"ChatOpen"} ]

Big-endian (network byte order) is the convention every internet protocol uses for multi-byte integers — both peers must agree, and x86/ARM CPUs are little-endian, so the code converts explicitly with shifts rather than casting an int's raw bytes:

frame.push_back(static_cast<char>((len >> 24) & 0xFF));  // most significant first
frame.push_back(static_cast<char>((len >> 16) & 0xFF));
frame.push_back(static_cast<char>((len >> 8) & 0xFF));
frame.push_back(static_cast<char>(len & 0xFF));

Reassembly: the accumulate-and-peel loop

bool FrameAssembler::feed(bytes, onFrame) {
    buffer_.append(bytes);                    // whatever recv() gave us
    while (buffer_.size() >= 4) {             // enough for a prefix?
        uint32_t declared = readPrefix(buffer_);
        if (declared > kMaxFrameBytes) return false;   // see below
        if (buffer_.size() < 4 + declared) return true; // wait for more
        onFrame(buffer_.substr(4, declared)); // complete frame!
        buffer_.erase(0, 4 + declared);       // peel and repeat
    }
    return true;
}

Bytes can arrive split anywhere — mid-prefix, mid-payload — and multiple frames can arrive in one read. The loop handles both: it buffers until a whole frame exists, emits it, and keeps going. tests/test_net_framing.cpp feeds a frame one byte at a time to prove it.

The poisoned-prefix problem

If a prefix is corrupt (or hostile) and declares a 3 GB payload, a naive reader allocates 3 GB and waits forever. Worse: once you mistrust one prefix, you can never find the next frame boundary again — the stream is unrecoverable.

That's why feed() returns false when the declared length exceeds kMaxFrameBytes (1 MiB — generous, since a 4-player snapshot is a few KB), and why the caller's only correct response is to drop the connection. There is no "skip this frame": without trusting the length, you don't know where it ends.

Contrast: StreamAssembler vs FrameAssembler

The two classes are siblings — same feed/callback shape, different boundary rule:

  • StreamAssembler::feed() scans for \n; unbounded line length (trusts Ollama).
  • FrameAssembler::feed() reads a declared size; bounded, endian-explicit, drop-on-violation (trusts nobody).
Design takeaway: when you control both ends of a socket, a length prefix is almost always the simplest robust choice. Reach for delimiters only when a protocol you don't control already promises them.
