1. Connection Ports — What They Really Are

Every hardware block on the canvas has connection ports — the small blue circles on its edges. In Python they are instances of ConnectionPort, which is a child QGraphicsItem embedded inside the block.

What each port holds

AttributeTypeWhat it means
port_idstrUnique name within the block (e.g. "CH1_IN")
labelstrShort display label painted near the circle
parent_blockBaseBlockThe block this port belongs to
connected_toOptional[ConnectionPort]None when free; points to the peer port when wired

Position is fractional — not pixels

When a subclass calls add_port("CH1_IN", "CH1", 0.0, 0.15), the numbers 0.0 and 0.15 are fractions of the block's width and height:

# silmulator/gui/blocks/base_block.py:189
def add_port(self, port_id: str, label: str,
             x_frac: float, y_frac: float) -> ConnectionPort:
    port = ConnectionPort(self, port_id, label)
    # setPos is RELATIVE to the parent block's (0,0) corner
    port.setPos(self.BLOCK_WIDTH * x_frac,
                self.BLOCK_HEIGHT * y_frac)
    self._ports.append(port)
    return port

So x_frac=0.0 → left edge, x_frac=1.0 → right edge, y_frac=0.0 → top, y_frac=1.0 → bottom. This makes port placement resize-friendly — if you change BLOCK_WIDTH the ports move with it.

Colour signals connection state

● Blue = idle (free)   ● Green = connected   ● Gold = hover target 
# ConnectionPort._update_color()  — base_block.py:41
def _update_color(self) -> None:
    color = self.COLOR_CONNECTED if self.connected_to else self.COLOR_IDLE
    self.setBrush(QBrush(color))   # fills the circle
    self.setPen(QPen(QColor(30,30,30), 1.5))  # dark outline
💡 Key invariant
If portA.connected_to is portB, then portB.connected_to is portA. The link is always symmetric — connect_to() sets both sides at once.

2. Wires — How the Connection Is Stored and Drawn

A wire is a WireItem — a QGraphicsLineItem that lives in the scene, separate from both blocks. It holds references to its two endpoint ports and redraws itself on every mouse move.

# silmulator/gui/canvas.py:46
class WireItem(QGraphicsLineItem):
    def __init__(self, src: ConnectionPort, dst: ConnectionPort) -> None:
        super().__init__()
        self.src_port = src      # reference to source port
        self.dst_port = dst      # reference to destination port
        self.wire_id  = str(uuid.uuid4())[:8]
        pen = QPen(QColor(255,200,50), 2, ...)  # gold, 2 px wide
        self.setZValue(-1)       # render BELOW blocks so ports stay visible
        self.update_position()   # draw the initial line

    def update_position(self) -> None:
        src_pos = self.src_port.scenePos()   # world-space coords
        dst_pos = self.dst_port.scenePos()
        self.setLine(QLineF(src_pos, dst_pos))

The wire's ZValue is -1 — it renders below all blocks. That's intentional: you should always be able to see and click the port dots even when two blocks are close together.

What happens when you connect two ports

# CanvasScene.connect_ports()  — canvas.py:185
def connect_ports(self, src: ConnectionPort,
                   dst: ConnectionPort) -> Optional[WireItem]:
    # Guard 1: no self-loops
    if src.parent_block is dst.parent_block:
        return None
    # Guard 2: no overwriting existing connections
    if src.connected_to or dst.connected_to:
        return None

    wire = WireItem(src, dst)
    self.addItem(wire)                          # add to scene
    self._wires[wire.wire_id] = wire            # register in bookkeeping dict
    src.connect_to(dst)                         # sets both port.connected_to
    self.wire_added.emit(...)

What happens when you delete a block

The scene must remove all wires attached to that block first, then unregister the block:

# CanvasScene.remove_block()  — canvas.py:143
wires_to_remove = [
    w for w in self._wires.values()
    if (w.src_port.parent_block is block or
        w.dst_port.parent_block is block)
]
for wire in wires_to_remove:
    self._remove_wire(wire)    # calls port.disconnect() on both ends
⚠ The disconnect contract
port.disconnect() sets self.connected_to = None and sets the peer's connected_to = None. If you delete the WireItem from the scene without calling disconnect(), the two ports still think they're connected — a ghost state that breaks future connection attempts.

3. In This Project — Reading Real Port Definitions

Every block subclass overrides _setup_ports() to declare its port layout. Here are two contrasting examples:

Oscilloscope — input ports on the left, trigger on the right

# silmulator/gui/blocks/oscilloscope_block.py:41
def _setup_ports(self) -> None:
    for i in range(1, 5):
        # x=0.0 → left edge; y stacks down: 0.15, 0.35, 0.55, 0.75
        self.add_port(f"CH{i}_IN", f"CH{i}", 0.0, 0.15 + 0.2 * (i - 1))
    # x=1.0 → right edge; y=0.5 → vertical middle
    self.add_port("TRIG_IN", "TRIG", 1.0, 0.5)

MSP430 — GPIO on both sides, specials at top and bottom

# silmulator/gui/blocks/msp430_block.py:29
def _setup_ports(self) -> None:
    for i in range(8):
        self.add_port(f"P1.{i}", f"P1.{i}", 0.0, 0.2 + 0.08 * i) # left
        self.add_port(f"P2.{i}", f"P2.{i}", 1.0, 0.2 + 0.08 * i) # right
    for i in range(4):
        self.add_port(f"ADC{i}", f"A{i}", 0.15+0.2*i, 1.0) # bottom
    self.add_port("VCC",  "VCC",  0.5, 0.0) # top
    self.add_port("GND",  "GND",  0.7, 0.0) # top
    self.add_port("UART_TX", "TX", 0.0, 0.95) # near bottom-left

The pattern: inputs left (x=0.0), outputs right (x=1.0), power top (y=0.0), comms bottom (y=1.0). This is a convention, not enforced — the system accepts any (x, y) fraction.

How save/load captures connections

# canvas.py:to_dict() — what gets serialised
"wires": [
    {
        "id":        wire.wire_id,
        "src_block": wire.src_port.parent_block.block_id,
        "src_port":  wire.src_port.port_id,     # e.g. "CH1_OUT"
        "dst_block": wire.dst_port.parent_block.block_id,
        "dst_port":  wire.dst_port.port_id,     # e.g. "CH1_IN"
    }
]

On load, from_dict() rebuilds a port_map keyed by (block_id, port_id), then calls connect_ports() for each wire entry. If a block was silently skipped (e.g. the old "Function Gen" name mismatch) its port_id entries are missing from the map — that wire is simply dropped.

4. hardware_docs/ — The Reference Layer

The hardware_docs/ folder is where you put vendor documentation so it ships alongside the simulator. It has nothing to do with code generation automatically — it is a human-readable reference store that a future "New custom block from docs…" wizard will read.

hardware_docs/
├── keysight/     ← E36312A, 33522B, 34401A programmer's references
├── tektronix/    ← MSO54, TBS series
├── ti/           ← MSP430FR5994, C2000 series
├── nasa/         ← cFE, cFS, F′ Prime flight OS docs
├── rtos/         ← FreeRTOS, Zephyr, NuttX programmer's guides
└── custom/       ← in-house ASICs, development boards, anything else

The suggested per-device layout

hardware_docs/keysight/E36312A/
├── programmer_reference.pdf   ← the full vendor PDF
├── scpi_commands.md           ← cleaned-up command table you'll test against
└── notes.md                   ← team-specific notes (quirks, tested versions)

What Silmulator currently does with these files

File typeWhat happens
PDFsStored for human reference; not auto-parsed at runtime
scpi_commands.mdThe future custom-block wizard will read this to pre-fill command maps
notes.mdHuman reference only
💡 The workflow loop
  1. Drop a vendor PDF in hardware_docs/<vendor>/<model>/
  2. Write a scpi_commands.md summarising the commands you'll test
  3. Create a matching JSON spec in silmulator/custom_blocks/
  4. Restart Silmulator — the block appears in the library automatically

Why a folder, not a wiki

Lab benches, secure test ranges, and flight-test environments often have no internet. Keeping docs in the git repo means the Docker image and .app bundle always ship with the references your test code was written against — no "where's that PDF" hunt during a test campaign.

5. Custom Blocks — Creating Instruments Without Writing Python

The custom-block system lets you define a new instrument entirely in a JSON file. Drop it in silmulator/custom_blocks/ (or ~/.silmulator/custom_blocks/ for personal blocks) and it appears in the library on next launch.

The minimal spec — Hello World example (shipped with Silmulator)

// silmulator/custom_blocks/hello_world.json
{
    "name":         "Hello World",
    "manufacturer": "Silmulator",
    "model":        "HELLO-1",
    "color":        "#3a6f3a",    // CSS hex — the block header tint
    "ports": [
        {"id":"IN",  "label":"IN",  "x":0.0, "y":0.5},  // left-middle
        {"id":"OUT", "label":"OUT", "x":1.0, "y":0.5}   // right-middle
    ],
    "commands": {
        "HELLO":  "world",        // any matching command → always returns "world"
        "*IDN?":  "Silmulator,HELLO-1,SIM000001,1.0.0",
        "ECHO":   "echo:{0}"     // {0} substitutes the first SCPI parameter
    }
}

Three command value types

Value formatMeaningExample
"some string"Always returned verbatim"HELLO": "world"
"" (empty)Write-only — accepted, no response"OUTP": ""
"echo:{0}"Substitutes SCPI positional paramsECHO 42 → "echo:42"

How discovery works at startup

# canvas.py:40 — runs at import time
try:
    register_custom_blocks(BLOCK_REGISTRY)
except Exception:
    pass   # one bad JSON file cannot block app startup

register_custom_blocks() calls discover_specs() which glob("*.json")s both silmulator/custom_blocks/ and ~/.silmulator/custom_blocks/. Each valid spec is turned into a live Python class by make_custom_block_class(spec) and added to BLOCK_REGISTRY — the same dictionary the built-in blocks live in.

📌 The full pipeline
hardware_docs/keysight/E36312A/scpi_commands.md → (you author a spec) → silmulator/custom_blocks/keysight_e36312a_custom.json → (app starts) → discover_specs() → make_custom_block_class() → appears in Library panel as "Keysight E36312A Custom"

6. Often Confused: Ports vs. Wires vs. Signals

Three things in this project carry the word "connection" — they are completely different layers:

ConceptPython classWhereWhat it does
Port ConnectionPort base_block.py A clickable endpoint on a block. Holds connected_to reference. Visual + structural.
Wire WireItem canvas.py A drawn line between two ports. Lives in the scene. Routes Code Input commands when _get_connected_blocks() is called.
Qt Signal pyqtSignal canvas.py A Python-level event notification (e.g. wire_added). Carries metadata to listeners like the status bar. Not visible on canvas.

Common confusion: people think wires route SCPI commands in real-time, like a bus. They don't — a wire's only runtime effect is to be traversed by _get_connected_blocks() when the Code Input block runs its parsed commands. For direct console commands the wire is purely visual.

PortWireQt Signal
Visible on canvas?✓ blue/green circle✓ gold line✗ invisible
Persisted in layout file?✓ (via block)✓ src_block/port + dst_block/port✗ ephemeral
Routes SCPI commands?✗Only for Code Input → connected blocks✗
One per block?✗ (many)✗ (many)✗ (several types)

7. Quiz

Q1. You call add_port("TRIG_IN", "TRIG", 1.0, 0.5) on a block with BLOCK_WIDTH=300 and BLOCK_HEIGHT=220. Where does the port appear, in pixels relative to the block's top-left corner?

  • x=300, y=110 — right edge, vertical midpoint
  • x=0, y=110 — left edge, vertical midpoint
  • x=150, y=110 — horizontal midpoint, vertical midpoint
  • x=300, y=220 — right edge, bottom edge

Q2. After connect_ports(portA, portB) succeeds, what is the value of portA.connected_to?

  • True
  • portB — the peer ConnectionPort object
  • The WireItem that connects them
  • None

Q3. You drop a JSON file at ~/.silmulator/custom_blocks/my_device.json. When does the block appear in the Library panel?

  • Immediately — the app watches the folder and hot-reloads
  • On the next application restart — discovery runs at import time
  • After right-clicking the canvas and choosing 'Refresh block library'
  • Only if you also add it to BLOCK_REGISTRY manually in canvas.py

Q4. What does a WireItem's setZValue(-1) accomplish?

  • It makes the wire non-interactive so port clicks aren't intercepted
  • It makes the wire draw in red to indicate low priority
  • It renders the wire behind all blocks so port dots remain visible on top
  • It hides the wire until a block is selected

  • echo:{0}
  • echo:hello
  • '' (empty string — write-only)

8. Scenarios — Check Your Understanding

Scenario A: You want to simulate a custom relay board that has 4 output channels and responds to the commands RELAY:CH1 ON, RELAY:CH1 OFF, and RELAY:CH1? (returns "ON" or "OFF"). Describe the JSON spec you'd write — name the required fields and what you'd put in each.
Show answer 
{
  "name": "Relay Board",
  "manufacturer": "MyLab",
  "model": "RB-4CH",
  "color": "#5a3a1a",
  "ports": [
    {"id":"CH1","label":"CH1","x":1.0,"y":0.2},
    {"id":"CH2","label":"CH2","x":1.0,"y":0.4},
    {"id":"CH3","label":"CH3","x":1.0,"y":0.6},
    {"id":"CH4","label":"CH4","x":1.0,"y":0.8}
  ],
  "commands": {
    "RELAY:CH1":  "",       // write ON/OFF — write-only, no response
    "RELAY:CH1?": "ON",     // simplest stub: always returns "ON"
    "RELAY:CH2":  "",
    "RELAY:CH2?": "OFF",    // etc.
    ...
  }
}

Note: the current custom-block system can't store state between commands (a real ON/OFF toggle), so RELAY:CH1? always returns the same literal. State-tracking requires a Python device class. The JSON spec is ideal for stateless instrument stubs.

Scenario B: You load a saved layout and notice that one block's wires are missing — they were there when you saved. Name two bugs that could cause this, and how each manifests in the code.
Show answer

Bug 1 — device_type mismatch: The block's device_type string (set in __init__) doesn't match its key in BLOCK_REGISTRY. to_dict() stores the wrong string; from_dict() calls add_block(wrong_name) which returns None; the block is silently skipped; its ports never enter port_map; all wires referencing its ports are also skipped. (This was the Function Generator bug.)

Bug 2 — clear() not resetting registries: After File → New the old block/wire registries aren't cleared. On the next from_dict(), stale entries from the previous layout could interfere with the port_map build — older block_ids might shadow new ones with the same UUID prefix. (Fixed by the CanvasScene.clear() override.)

Scenario C: A colleague asks "Why do wires have ZValue=-1? Couldn't we just put them at ZValue=0 like everything else?" Give the technical reason.
Show answer
Qt renders higher ZValue items on top. Blocks have ZValue=0 (the default). If wires were also at 0, the render order between a wire and a block would be undefined — Qt renders same-ZValue items in scene-item order (last added on top). A wire added after a block would render above it, potentially covering the port circles. Setting ZValue=-1 guarantees wires are always below all blocks so ports stay visible and clickable regardless of how many wires cross through a block's bounding rect.
