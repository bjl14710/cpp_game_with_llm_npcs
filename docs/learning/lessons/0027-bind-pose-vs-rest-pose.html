Bind Pose vs Rest Pose in glTF Skinning

From session 9 (issues #139/#142): why the Quaternius characters froze in a T-pose with moving fingers — and the one matrix that fixed both the statues and the walk cycle.

Two different "default poses" live in one glTF file

A skinned glTF carries two skeleton configurations, and nothing forces them to match:

Where it livesWhat it means
Bind pose skins[0].inverseBindMatrices (one inverse matrix per joint) — and implicitly in the mesh vertices, which are stored in this pose The pose the mesh was skinned in (usually a T- or A-pose, arms out so weight painting is easy)
Rest pose Each joint node's local translation/rotation/scale, composed down the node hierarchy The skeleton's default stance when no animation plays (often a natural arms-down pose)

The skinning equation ties them together. For a vertex v stored in bind space:

v' = Σj wj · Gj(pose) · IBMj · v

IBM (inverse bind matrix) takes the vertex from bind space into the joint's local space; the joint's global pose matrix G takes it back out into whatever pose is playing. Skip the IBM and you silently assume bind == rest.

The symptom we chased

Fingers animated, shoulders didn't. The pack's characters stood in a T-pose; Idle/Walk clips moved fingers, elbows, and legs, but the arms stayed horizontal forever. Death collapsed the body — with the arms still out.

Every hypothesis that blames the data fails in turn (we checked: arm bones are targeted by LINEAR rotation channels; joints are topologically sorted; no unbaked IK bones). The decisive test was computing, from raw JSON alone, the global wrist position in the rest pose: (±0.25, 1.01) — hip height. The rest pose has the arms down. The animation keeps joints near rest, i.e. near arms-down. The data was right all along.

The engine assumption

raylib's glTF loader never reads inverseBindMatrices. It builds model.bindPose from the joint nodes' world transforms — the rest pose — and its CPU skinning computes deltas relative to that:

boneMatrixj ≈ Gj(anim) · Gj(rest)-1   // rest-relative delta
v' = Σ wj · boneMatrixj · v          // v assumed stored in REST space

That convention is fine when bind == rest (most exporters, including KayKit's, do this — which is why those characters animate perfectly). This pack stores vertices in T-pose bind over an arms-down rest: for arm joints the animation ≈ rest, so the delta ≈ identity, so the T-pose vertices render unchanged. Legs matched between the two poses — that's why they moved.

The fix: re-bake vertices into the engine's convention, once

// at load, per vertex (Assets.cpp, rebakeVerticesToRestPose):
skinMat[j] = restGlobal[j] * inverseBind[j];      // bind space -> rest space
v_rest     = Σ w_j * skinMat[boneId_j] * v_bind;  // write back + re-upload VBO

One transform at load and both tiers snap into place: static (unanimated) characters stand in the natural arms-down rest pose, and UpdateModelAnimation's rest-relative deltas become exactly right, so Idle/Walk play as authored. The IBMs came from the glTF's own JSON (it's the same file the model loader parses; the buffer is a base64 data: URI — raylib's DecodeDataBase64 reads it).

Bonus insight: because every file in the pack shares one skeleton and animation library, posing a head-model and a body-model with the same clip at the same time makes a mixed head (witch head on soldier body) ride its neck bone perfectly — bone attachment with no attachment code.

How to recognize this bug in the wild

  • Partial animation — some limbs move, others freeze. The frozen ones are where rest ≠ bind; the moving ones are where they agree.
  • The model looks right in Blender/Bevy/three.js (they apply IBMs) but wrong in your engine.
  • Ground-truth from data, not from renderers: glTF is JSON — compose the node hierarchy yourself and print a wrist position. Ten lines of python ends the guessing.
