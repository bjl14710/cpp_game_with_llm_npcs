Hardware Docs & Custom Blocks

Why this matters: Silmulator ships with six built-in blocks. Every real test bench has instruments that aren't in the list — learning this workflow lets you add any device in minutes, not days.

§0 The two-folder system

Adding a new hardware device to Silmulator is a two-step process. Two folders play different roles:

hardware_docs/ ← source of truth: vendor PDFs, programmer's refs ├── keysight/ │ └── E36312A/ │ ├── programmer_reference.pdf │ ├── scpi_commands.md ← wizard reads this first │ └── notes.md ├── tektronix/ ├── ti/ ├── nasa/ ├── rtos/ └── custom/ silmulator/custom_blocks/ ← executable specs auto-loaded at startup ├── __init__.py └── hello_world.json ← the one committed example

hardware_docs/ is the reference library. Drop PDFs, programmer's guides, and extracted SCPI tables here. Nothing in this folder runs automatically — it ships alongside the simulator so engineers on a test bench can consult the original docs without leaving the project.

silmulator/custom_blocks/ is the executable layer. Every .json file here is auto-discovered at startup and appears in the block palette. Think of it as "derived from the docs, ready to simulate."

§1 hardware_docs/ — reference library

Silmulator/hardware_docs/README.md

Layout convention

There are no enforced file names, but the established pattern is:

hardware_docs/ └── <vendor>/ ← lowercase vendor name └── <model>/ ← model number or family ├── programmer_reference.pdf ├── scpi_commands.md ← optional: cleaned-up command table └── notes.md ← team-specific notes

The scpi_commands.md convention

The custom-block wizard (right-click canvas → New custom block from docs…) reads scpi_commands.md first when it exists in a model folder. The format is a simple markdown table:

| Command       | Direction | Response / Notes            |
|---------------|-----------|-----------------------------|
| VOLT <n>      | write     | Sets output voltage         |
| VOLT?         | query     | Returns current voltage     |
| OUTP ON\|OFF   | write     | Enables/disables output     |
| *IDN?         | query     | Manufacturer identification |
| *RST          | write     | Factory reset               |

This table is human-readable and is what the wizard uses to pre-fill the JSON spec. You don't have to follow this format exactly — any markdown that lists command names and their directions is useful.

Long-form PDFs

PDFs are not parsed automatically. They live here for two reasons:

  • Offline access — lab benches, secure rooms, and flight-test ranges often have no network. The PDF ships inside the Docker image and installers.
  • Traceability — when a test fails because a SCPI command behaves unexpectedly, you can pull up the original programmer's reference alongside the running simulation.
Adding a new vendor is four lines in the terminal: mkdir -p hardware_docs/newvendor/ModelXX && cp reference.pdf hardware_docs/newvendor/ModelXX/. No code changes required.

§2 The JSON spec format

silmulator/custom_blocks/hello_world.json

Every file in custom_blocks/ is a self-describing JSON object. Here is the committed example with every field annotated:

{
    "name": "Hello World",          ← appears in block palette and BLOCK_REGISTRY
    "manufacturer": "Silmulator",  ← shown on the block face
    "model": "HELLO-1",            ← *IDN? manufacturer and model fields
    "color": "#3a6f3a",          ← any CSS hex color — becomes BODY_COLOR

    "ports": [
        {"id": "IN",  "label": "IN",  "x": 0.0, "y": 0.5},  ← left edge, centered
        {"id": "OUT", "label": "OUT", "x": 1.0, "y": 0.5}   ← right edge, centered
    ],

    "commands": {
        "HELLO":   "world",              ← literal response
        "*IDN?":   "Silmulator,HELLO-1,SIM000001,1.0.0",
        "ECHO":    "echo:{0}"            ← template: {0} = first parameter
    }
}

Port coordinates — x/y fractions

x and y are fractions of the block's width (220 px) and height. The block height is computed from the port count: max(120, 40 + 20 × max(1, port_count)).

x=0.0, y=0.5 → left edge, vertical center (typical IN port) x=1.0, y=0.5 → right edge, vertical center (typical OUT port) x=0.0, y=0.25 → left edge, upper quarter x=0.5, y=0.0 → top edge, horizontal center

Three command response types

TypeExample valueWhat it does
Literal"pong"Always returns this exact string
Empty""Write-only — accepted, no response
Template"echo:{0}"Substitutes SCPI parameters: {0}=first param, {1}=second, etc.
Command keys are normalized to UPPERCASE by BlockSpec.from_dict() (line 88 of custom_block.py). You can write "volt" or "VOLT" — both become "VOLT" in the handler table.

§3 The discovery pipeline

Three functions run in sequence:

discover_specs()

166def discover_specs(extra_dirs=None):

176    if PACKAGED_DIR.exists(): dirs.append(PACKAGED_DIR)    # custom_blocks/

register_custom_blocks()

195def register_custom_blocks(registry, extra_dirs=None):
198    specs = discover_specs(extra_dirs)
199    for spec in specs:
200        registry[spec.name] = make_custom_block_class(spec)  # add to BLOCK_REGISTRY
201    return specs

Result: BLOCK_REGISTRY["My Device"] = <class Custom_My_Device>. From this point on, the block appears in the Add menu, can be instantiated, saved, and reloaded exactly like a built-in.

User directory

The second scan path is ~/.silmulator/custom_blocks/. Drop a JSON file there for blocks that are personal to you (a test fixture, a prototype, an in-house ASIC) without modifying the shared repo. The packaged blocks are found first — if a user block has the same name as a packaged block, the packaged version wins (first-seen wins on line 189).

§4 Response patterns in depth

silmulator/gui/blocks/custom_block.py:114–124

Every command value goes through _make_handler(template), which returns a closure:

114def _make_handler(template: str) -> Callable:
115    def handler(cmd: ScpiCommand) -> str:
116        if not template:
117            return ""                        ← empty string → write-only
118        if "{" not in template:
119            return template                   ← no braces → literal
120        try:
121            return template.format(*cmd.params)  ← braces → template substitution
122        except (IndexError, KeyError):
123            return template                   ← wrong param count → return as-is
124    return handler

Concrete examples:

JSON commandSCPI sentResponse
"PING": "pong"PINGpong
"VOLT": ""VOLT 5.0(no response)
"ECHO": "echo:{0}"ECHO 42echo:42
"MUL": "{0}×{1}"MUL 3 73×7
"STATUS?": "OK"STATUS?OK
The command key is matched after the ? is stripped and everything is uppercased by ScpiParser. A JSON command named "STATUS?" is normalized to key "STATUS" in the handler table (line 110: normalized = cmd_path.rstrip("?")). So "STATUS" and "STATUS?" in the JSON both map to the same handler — they are equivalent.

§5 The authoring workflow, end-to-end

  1. Get the manual. Download the programmer's reference PDF from the vendor site (Keysight, Tektronix, etc.). If it's a proprietary ASIC, export the command register map from your design tool.
  2. Drop it in hardware_docs/. Create hardware_docs/<vendor>/<model>/. Drop the PDF there.
  3. Extract the SCPI table. Open the PDF, find the "SCPI Command Reference" section (usually an appendix). Copy out the commands you plan to test into a scpi_commands.md file in the same folder.
  4. Write the JSON spec. Create silmulator/custom_blocks/<vendor>_<model>.json. Map each command from step 3 to a response pattern (literal / empty / template).
  5. Restart Silmulator. The block appears automatically in the palette. No Python required.
  6. Test it. Add the block, right-click → Send SCPI command. Verify each command returns what you expect.
  7. Wire it. Connect a Code Input block (containing your firmware) to the new block and run parsed commands. Check the command log.

Live iteration — no restart needed

During step 4, you can use discover_specs(extra_dirs=[Path("my_specs/")]) from a Python REPL to check your JSON without restarting the GUI. The test suite in tests/test_custom_blocks.py follows this pattern — it writes specs to a tmp_path and calls discover_specs(extra_dirs=[tmp_path]).

§6 JSON spec vs Python subclass — when to use which 




  
CapabilityJSON specPython subclass

  
No Python required✓✗

  
Appears on restart without code changes✓✗ (need to import)

  
Stateful simulation (e.g. track voltage after VOLT N)✗✓

  
Computed responses (math, noise, waveform data)✗✓

  
Custom block face UI (graphs, meters)✗✓

  
IEEE 488.2 common commands (*IDN?, *RST, etc.)manual in JSON✓ inherited from BaseDevice

  
Per-user without repo changes✓ (~/.silmulator/)✗





Use a JSON spec when: you need to test that your firmware sends the right commands to a device and you only care about static/literal responses. Good for protocol-level verification: "does my code send VOLT 5.0 before OUTP ON?"


Use a Python subclass when: you need the device to actually track state — e.g. the Power Supply remembers the set voltage and returns it (plus noise) on MEAS:VOLT:DC?. The built-in OscilloscopeBlock, PowerSupplyBlock, etc. are all Python subclasses for exactly this reason.


The upgrade path: start with a JSON spec to verify protocol correctness quickly, then promote it to a Python subclass when you need stateful simulation. The JSON spec's command table becomes the skeleton for _setup_handlers().

Q2. Your JSON spec has "volt": "5.0" (lowercase key). A firmware test sends VOLT?. What does the block return?


    
  
  • Nothing — the '?' suffix is not stripped so the handler lookup for 'volt' fails against the incoming 'VOLT?' path.
    • 
  
  • 5.0 — BlockSpec normalizes all keys to uppercase, and ScpiParser strips '?' before dispatch.
    • 
  
  • Nothing — the lowercase JSON key 'volt' doesn't match the uppercase normalized path 'VOLT'.
    • 
  
  • A noisy float near 5.0 — custom blocks apply the same measurement simulation as the built-in Power Supply.
    • 











Q3. You drop a broken JSON file (invalid syntax) in silmulator/custom_blocks/. What happens to the other blocks in that folder?


    
  
  • The GUI fails to start because discover_specs() propagates the JSON parse exception up through register_custom_blocks() into canvas.py.
    • 
  
  • The broken file is skipped silently and all valid JSON specs in the same folder are still registered. Silmulator starts normally.
    • 
  
  • The broken file stops processing of any files created after it (discover_specs reads files in creation order and stops on the first error).
    • 
  
  • discover_specs() writes an error log to silmulator/custom_blocks/errors.log and skips the broken file.
    • 











Q4. You have two JSON specs with "name": "SpectrumAnalyser" — one in silmulator/custom_blocks/ and one in ~/.silmulator/custom_blocks/. Which one wins?


    
  
  • The user directory wins — ~/.silmulator/ is always preferred over packaged blocks so users can override defaults.
    • 
  
  • An error is raised — duplicate block names are not allowed and the GUI reports the conflict at startup.
    • 
  
  • The packaged one wins — silmulator/custom_blocks/ is scanned first. First-seen wins on duplicate names.
    • 
  
  • The one with more commands wins — discover_specs() merges duplicate-named specs, keeping the richer command set.
    • 











Q5. When should you write a Python subclass (like PowerSupplyBlock) instead of a JSON spec?


    
  
  • When you want the block to appear in the block palette (JSON specs don't register with BLOCK_REGISTRY).
    • 
  
  • When the device needs IEEE 488.2 common commands (*IDN?, *RST) — these require a Python BaseDevice subclass.
    • 
  
  • When the device needs stateful simulation: it must remember configured values, compute responses from state, or generate waveform data.
    • 
  
  • When you want the block to be available only to you (per-user), not shared in the repository.

Scenario questions




  
You write a JSON spec for a network analyser. It needs to respond to FREQ:START 1E6 (set start frequency, no response) and FREQ:START? (query current start frequency, must return whatever was last set). Can you implement this in JSON? What's the limitation?

  
  
No — not fully. The write command "FREQ:START": "" is easy (empty string = accepted, no response). But the query "FREQ:START?": "1000000.0" can only return a hardcoded literal, not the value that was last set. JSON specs have no state — there's no way to store the value written by the SET command and return it on the query. For this you need a Python subclass with an instance variable that the write handler updates and the query handler reads. The JSON spec can approximate it with a hardcoded default, which is fine for sanity-checking that the firmware sends the right command format.






  
You're a new team member. You write silmulator/custom_blocks/my_oscilloscope.json but the block never appears in the palette no matter how many times you restart. What are three things to check?

  
  
1. JSON syntax error — run python -c "import json; json.load(open('my_oscilloscope.json'))". A parse error causes discover_specs() to silently skip the file.
2. Missing "name" field — BlockSpec.from_dict() raises ValueError("custom block spec missing 'name'") which is also caught and skipped.
3. Name collision — another spec (packaged or user) already claims the same "name" value. The first-seen wins. Check: discover_specs() with debug prints, or temporarily rename the name field to something unique.
Bonus: confirm the file lives in custom_blocks/ (not hardware_docs/ or some other folder) and ends in .json (not .json.bak or .JSON).






  
Your firmware sends ECHO Hello World to a block with "ECHO": "echo:{0}". ScpiParser splits the command: path="ECHO", params=["Hello", "World"]. What does the block return?

  
  
echo:Hello. The template is "echo:{0}". {0} substitutes the FIRST parameter only — params[0] is "Hello". params[1] ("World") is not referenced and is ignored. The format string is called as "echo:{0}".format("Hello", "World") which returns "echo:Hello". To include both parameters you'd need "echo:{0} {1}".
