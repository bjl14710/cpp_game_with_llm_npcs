Deterministic Tests for Threaded Socket Code

The loopback suite spins up a real server, real clients, and a fake LLM — and passes every time. Here's the discipline that makes that possible.

Test the real stack, fake the boundary

tests/test_net_loopback.cpp does not mock NetServer or NetClient — it runs both over 127.0.0.1, because the threading and framing are the things under test. What it fakes is the external boundary: FakeOllama plays the LLM (canned streamed replies, error modes like Http500). The rule of thumb:

Fake what you don't own (Ollama's HTTP API). Run what you do own (your sockets, your threads, your router) for real — on the loopback interface, where the network is fast and private.

Two tricks make real sockets test-friendly:

  • Port 0: asking the OS to bind "any free port" (then reading it back with getsockname) means parallel test runs never collide on a hardcoded port.
  • The fixture mirrors production wiring: ChatLoopback::hostFrame() is the same three-line pump main.cpp runs per frame. If the fixture wiring diverges from the game's, the tests verify a program nobody ships.

Never sleep and hope

The cardinal sin of async testing:

client.sendInput(...);
std::this_thread::sleep_for(200ms);          // "should be enough"  ← flake factory
CHECK(snapshotArrived());

Too short on a loaded CI machine → false failure. Long enough to be safe → the suite crawls. The loopback suite's replacement is predicate polling with a deadline:

bool eventually(predicate, pump, deadline = 3000ms) {
    auto end = now() + deadline;
    while (now() < end) {
        if (pump) pump();          // drive the host frame / drain clients
        if (predicate()) return true;   // succeed the instant it's true
        sleep_for(5ms);
    }
    return false;                  // honest failure with a bounded wait
}

Fast when the system is fast (usually a few milliseconds), honest when it hangs (bounded, reports failure). The pump parameter matters: shared-NPC chat needs the host loop to keep draining queues while we wait, exactly like the real game loop would.

Force the ugly interleavings

Concurrency bugs live in orderings that "never happen" on a fast machine. Good suites force them:

  • FakeOllama serves responses in 7-byte chunks so JSON always splits mid-token across TCP reads — the framing gets no easy days.
  • The framing test feeds a wire frame one byte at a time.
  • The ordering test waits until the NPC is busy with player A's question before sending player B's — making the queue-contention path deterministic instead of accidental.
  • The regression test for the LlmClient deadlock constructs and destroys the client 200 times — hammering the exact destructor-vs-wait window.

Flake checks: run it again. And again.

One green run of threaded code proves little — the schedule you got is one of millions. Tonight's protocol was for i in 1..8: ./run_tests after each networking change, and it paid for itself immediately: run 3 of the first batch hung, exposing a pre-existing lost-wakeup deadlock in LlmClient's destructor (see lesson 0011) that had nothing to do with the new code — the new tests just rolled the dice more often.

When a threaded test hangs, don't kill it — autopsy it first: sample <pid> (macOS) or gdb -p (Linux) shows every thread's stack. A deadlock diagnosis is usually two stack traces: who is waiting, and who was supposed to wake them.
