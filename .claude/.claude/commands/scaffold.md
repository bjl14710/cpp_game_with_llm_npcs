---
description: Scaffold the files and structure for a planned feature. Run after /idea has produced a plan doc in .claude/plans/. Reads the plan, reads the codebase, then creates the right files in the right places.
argument-hint: The plan name e.g. "visual-testing" or "weapon-shop" (matches the filename in .claude/plans/)
---

You are scaffolding the initial file structure for a planned feature.
This command bridges the gap between a plan document and actual files
on disk — creating skeletons, directories, config updates, and skill
files so the overnight session or /develop has something real to build on.

---

## STEP 1 — READ THE PLAN

```bash
# Find the plan document
ls .claude/plans/
cat .claude/plans/$1.md 2>/dev/null || \
  cat .claude/plans/$(echo "$1" | tr ' ' '-' | tr '[:upper:]' '[:lower:]').md 2>/dev/null || \
  echo "No plan found for '$1' — run /idea first"
```

If no plan exists, stop and tell the user to run `/idea` first.
The plan is the spec. Do not scaffold without it.

---

## STEP 2 — READ THE CODEBASE

```bash
# Understand what already exists before creating anything
find src/ lib/ app/ tests/ -type f 2>/dev/null | head -50
cat CLAUDE.md 2>/dev/null | head -50 || true
git log --oneline -10
```

Use real class names, real import paths, and real conventions from
what you find — not generic placeholders.

---

## STEP 3 — DERIVE WHAT NEEDS TO BE CREATED

From the plan's "Affected Areas" and "Implementation Order" sections,
determine:

- New directories needed
- New source files (with correct imports and skeleton structure)
- New test files (matching the project's test conventions)
- Config file updates (pytest.ini, CMakeLists.txt, requirements.txt etc.)
- New skill files if the feature introduces patterns Claude needs
  to reference repeatedly (e.g. a new API, a new framework)
- Any one-time setup scripts (e.g. installing system packages)
- .gitignore additions for generated or temporary files

---

## STEP 4 — CREATE THE FILES

For each file derived in Step 3:

**Source files** — create with:
- Correct imports based on existing patterns in the project
- Class/function skeleton matching the plan's interface
- Docstrings explaining what each piece does and why
- TODO comments marking what the overnight session needs to fill in
- No placeholder names — use real names from the codebase

**Test files** — create with:
- Correct pytest conventions for this project
- One test function stub per acceptance criterion in the plan
- Each stub has a docstring explaining what it tests
- `pytest.mark.skip(reason="not implemented yet")` on each stub
  so the test suite runs clean before the feature is built

**Config updates** — update existing files rather than creating new ones
where possible. Add only what the plan requires.

**Skill files** — only if the feature introduces something Claude needs
to reference repeatedly. Write to `.claude/skills/<feature>/SKILL.md`.
Not every feature needs a skill — only ones with non-obvious APIs,
protocols, or patterns.

**Setup scripts** — only if the feature requires one-time environment
setup (installing system packages, external tools, etc.). Write to
`scripts/setup-<feature>.sh`. Make it idempotent — safe to run twice.

---

## STEP 5 — DO NOT CREATE

Things the scaffold should NOT create:

- Implementation code (that's for /develop or the overnight session)
- Golden/reference files (those are generated by running the tests)
- Database migrations (those need careful human review)
- Secrets or credentials
- Anything not mentioned in the plan

If the plan is unclear about something, leave a clear TODO comment
and note it in the summary rather than guessing.

---

## STEP 6 — UPDATE .gitignore

Add any paths that should never be committed:
```bash
# Examples based on feature type:
# Visual testing:   tests/visual/diffs/  tests/visual/actual/
# Build artifacts:  dist/  build/  *.pyc
# Generated files:  whatever the feature produces at runtime

grep -qF "<path>" .gitignore || echo "<path>" >> .gitignore
```

---

## STEP 7 — SUMMARY

After creating all files, print a clear summary:

```
Scaffold complete for: [feature name]
Plan: .claude/plans/[plan].md

Files created:
  [path]  ← [one line: what it is]
  [path]  ← [one line: what it is]

Files updated:
  [path]  ← [what was added]

Next steps:
  1. [Any one-time setup to run e.g. bash scripts/setup-x.sh]
  2. Review the scaffolded files and adjust if needed
  3. /plan-github "[feature name]" to create GitHub issues
  4. bash ~/scripts/nightly.sh to build overnight
     OR /develop [feature] to build now

Nothing is implemented yet — stubs and skeletons only.
The overnight session or /develop fills them in.
```

---

## TONE

The scaffold is a starting point, not a finished product. Be explicit
about what is a skeleton vs what is complete. Use TODO comments
liberally — they are communication to the implementer, not a sign
of incompleteness in the scaffold itself.
